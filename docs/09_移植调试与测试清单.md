# 09 | 从 0 到 1 移植：Keil / CubeIDE 双工程与调试清单

## 一、建立两个互相独立的 STM32H723VE 工程

建议先在 STM32CubeMX / STM32CubeIDE 创建 `H723_Bootloader` 与 `H723_Application`，两边选择同一个 MCU 型号 `STM32H723VE`，先分别实现 LED 翻转或 UART 打印；验证每个工程单独编译正常，再开始互跳。**此仓库不包含你自己的完整 .ioc / HAL / startup / linker，不能直接作为可烧录完整 firmware 项目。**

### Bootloader 工程

- Flash 起始 `0x08000000`，长度 `0x20000` = 128KiB。
- 向量表 `.isr_vector` 位于 `0x08000000`。
- 使用 `configs/bootloader/MY_OTA_JUMP.h`（目标 `0x08020000`）。
- 加入原始 `.c` 或按安全参考修改后的跳转模块。
- 检查 `Reset_Handler` 会调用 `__libc_init_array`（若使用 constructor）。
- 在 Bootloader main 添加明确的“默认启动 APP / 等待升级”策略，否则冷启动仅运行 Bootloader。

### APP 工程

- Flash 起始 `0x08020000`，长度 `0x60000` = 384KiB。
- `.isr_vector` 位于 `0x08020000`；`SystemInit` 和后续初始化不能把 VTOR 错误地改回 Boot 基址。
- 使用 `configs/application/MY_OTA_JUMP.h`（目标 `0x08000000`）。
- 若采用“关闭全局中断直到 APP 初始化”的安全分支方案，APP 必须在正确阶段显式恢复 IRQ；注意 HAL Tick、延时和 FreeRTOS 依赖 IRQ。

## 二、检查头文件是否混用了

错误示范：Bootloader 里仍使用上传的 `MY_OTA_APP_ADDRESS=0x08000000`。这样 Bootloader 请求的目标就是自身，复位后 constructor 读到目标等于当前镜像，只会返回 Bootloader main，并不会进入 APP。

正确对应：

```text
Boot 当前 = 0x08000000 --> 目标 APP 0x08020000，上界 0x08080000
APP  当前 = 0x08020000 --> 目标 Boot 0x08000000，上界 0x08020000
```

## 三、保留 SRAM4 三个字

两个 linker/scatter 必须排除：`0x38003FF4 ... 0x38003FFF`。读 `.map` 检查是否有段/变量/栈/DMA 恰好占此区；若开启 MPU/Cache，先验证 Cache 属性及软件复位后读取是否一致。

## 四、逐阶段验证

### 阶段 1：证明单工程能启动

- 单独烧 Bootloader，检查 PC 是否落在 Boot `Reset_Handler`，能打印 BOOT READY。
- 单独烧 APP 到 `0x08020000`，通过调试器设 PC/MSP 或由 Bootloader 启动它（正常 BOOT 配置仍默认先到 Boot）；确认 APP 向量正确。
- 执行 `tools/check_vectors.py` 检查 APP.bin 前 8 字节。

### 阶段 2：测试 Boot → APP

1. 同时下载 Boot / APP 到各自区域，防止下载设置“全片擦除”覆盖另一镜像。
2. 在 Boot 打断点 `MY_OTA_JUMP_Request` 和 `MY_OTA_JUMP_CheckRequestAfterReset`。
3. 从 Boot UART 命令触发 `Request`。
4. 在复位前读 SRAM4：`MAGIC=0x4A554D50, TARGET=0x08020000, INV=~TARGET`。
5. 复位后命中 Boot constructor：检查 `current_address=0x08000000`；读取目标后请求被清空。
6. 命中 Boot `JumpNow`：APP MSP 位于允许 SRAM，APP Reset 位于 `0x08020000..0x0807FFFF`，bit0=1。
7. 单步到 APP Reset_Handler，再进入 APP main；核查 APP `SCB->VTOR=0x08020000`。

### 阶段 3：测试 APP → Boot

1. APP UART 发升级命令，调用 APP 的 `Request()`（目标 `0x08000000`）。
2. 软件复位后 PC 直接进入 Boot Reset_Handler。
3. Boot constructor 发现请求目标等于 `g_pfnVectors`，清除请求后继续 Boot main。
4. **不应该**再次调用一次 Boot->APP，除非 Boot main 的默认策略决定这样做；这是你需要自行控制的业务逻辑。

### 阶段 4：故障注入

- 擦空 APP 区，试 `IsApplicationValid` 是否为 0；
- 故意写入 Reset_Handler bit0=0 的镜像（在**离线样本**里检查，不建议破坏有用板子），确认脚本能识别；
- SRAM4 的 MAGIC 改错，重启后不得误跳；
- SRAM4 的 INV 改错，重启后不得误跳；
- APP 起点链接错误，检查 Reset 值是否落在目标区域；
- 开关编译优化观察 `JumpNow` 反汇编，尤其 MSP 设置之后有无访问旧栈；
- 模拟 SYSRESETREQ、硬复位、掉电，区分 SRAM 保持行为；
- APP `SystemInit()` 后检查 VTOR 有无被覆写；
- 若加入 FreeRTOS，确认已从 UART ISR 走软件复位，而不是从 PSP 任务中直接 `JumpNow()`。

## 五、串口中断集成示意

对于已有 `HAL_UART_RxCpltCallback` 工程，建议中断中只解析**短命令**：请求升级/复位可以直接调用 `MY_OTA_JUMP_Request()`；后续真正固件包解析和 Flash 写入则放在主循环或 RTOS 升级任务中，避免阻塞 UART IRQ。见 `../examples/uart_command_integration.c`。

## 六、用调试器观察哪些寄存器

| 断点位置 | 观察项 | 理想值（Boot→APP） |
|---|---|---|
| 复位前 | `JUMP_MAGIC` | `0x4A554D50` |
| 复位前 | `JUMP_TARGET` | `0x08020000` |
| Boot constructor | `(uint32_t)g_pfnVectors` | `0x08000000` |
| Boot JumpNow | APP `[BASE]` | 有效 SRAM 地址、8 字节对齐更好 |
| Boot JumpNow | APP `[BASE+4]` | `0x0802xxxx` ... `0x0807xxxx`，奇数 |
| Boot JumpNow | `SCB->VTOR` | `0x08020000` |
| APP Reset_Handler | `MSP` | APP 初始栈顶附近 |
| APP main | `SCB->VTOR` | `0x08020000` |
| 复位后 | SRAM4 三字段 | 归零（被一次性请求处理） |

## 七、如果出现 HardFault

1. 停在 Fault 时查看 `CFSR / HFSR / BFAR / MMFAR` 和当前 PC、LR、SP。
2. 如果 PC 指向 0x08000000 附近，可能 APP VTOR 被重置成 Boot；如果 PC 指向奇怪地址，检查向量表和 `Reset_Handler` bit0。
3. 如果 Fault 出现在 `__set_MSP()` 后，反汇编检查是否仍在用旧栈；参考纯汇编末级分支。
4. 如果在 APP 使用 UART/TIM 之后才报错，检查外围中断源、DMA、NVIC、Cache/MPU、外设反初始化。
5. 若 `.init_array` 从未执行，请检查启动汇编 `__libc_init_array` 和 `.map` 文件，而不是怀疑 SRAM4 先坏了。
6. 若是调试器复位后“丢了跳转标志”，先核实 Reset 类型、RAM 初始化脚本和 Debugger 下载/内存清除策略。

## 八、与 OTA 升级联调时应注意

永远不要把“能跳转 APP”直接当作“新固件升级成功”；至少增加镜像总长度、读取完整性、存储后读回、版本/签名验证、失败恢复策略，然后验证连续多次掉电和看门狗异常。具体见 06。
