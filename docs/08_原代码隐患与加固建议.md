# 08 | 对上传代码的工程性审查与加固建议

本页是**代码审查**，不是“原代码肯定运行失败”。有些写法在特定编译选项下可能恰好正常，但移植编译器、开优化或加 FreeRTOS 后有风险。

## 问题分级

| 优先级 | 现象/代码 | 可能的问题 | 建议 |
|---|---|---|---|
| **P0** | 修改 MSP 后继续执行普通 C 语句并调用函数指针 | 编译器可能继续使用被替换的栈帧 | 最后一步使用 `naked`/纯汇编分支；检查反汇编 |
| **P0** | 两工程头文件目标地址不同 | Boot 工程若误用上传 `.h`，会把自己当作目标 | 分开头文件，配置表见 README |
| **P0** | SRAM4 最后 12B 用固定地址 | 链接器、栈或 DMA 可能覆盖它们 | 两边 `.ld/.sct` 同时排除这 12B |
| **P1** | `__enable_irq()` 放在目标 Reset_Handler 之前 | 新固件未建立完整环境就可能中断 | 末级跳转保留中断屏蔽，由 APP 适当时刻打开 |
| **P1** | 仅有 `NVIC ICER/ICPR` | 系统异常 Pending 与外设 IRQ 来源没完全清 | 清 SysTick/PendSV Pending，必要时停外设/DMA |
| **P1** | `__attribute__((constructor))` | 不同编译器/启动库可能不执行 `.init_array` | 核实 `__libc_init_array` 和 `.map`；或改为 main 早期显式检查 |
| **P1** | MCU RAM 地址范围硬编码 | AXI SRAM 依配置、linker/MPU 可能不同 | 依据具体芯片和工程实际 RAM 布局检查 |
| **P1** | 只验证 MSP/Reset/Thumb 位 | 不能证明镜像完整/可信 | 升级时增加固件长度、Hash、签名与状态机 |
| **P1** | APP 的 `SystemInit()` 修改 VTOR | APP 启动后中断可能回 Boot 向量表 | APP 初始化末尾检查最终 `SCB->VTOR` |
| **P2** | 写跳转请求时 `MAGIC` 最先写 | 突然复位可留下部分新请求与旧字段 | 先写 TARGET、INV，最后写 MAGIC |
| **P2** | `IsStackValid` 用 `>=` 且不查 8 字节对齐 | 可能允许 RAM 段起点或未对齐 MSP | 检查 MSP 按 8 字节对齐、位于可用 RAM 栈顶 |
| **P2** | 依赖 SRAM4 SYSRESETREQ 可见性 | Cache/MPU 参数和 SRAM 保持路径可能有影响 | 结合 MPU/D-Cache 和调试器实测 |
| **P2** | 用户头文件注释写 `0x08020000` APP，但宏设 `0x08000000` | 容易把头文件用错工程 | 把“目标地址”写清，不固定叫 Application |
| **P3** | `#include "stdio.h"` 没用 | 无效依赖 | 可以删除 |

## A. `__set_MSP` 后应该怎样分支？

**原因**：C 函数可能已经在 Bootloader 的栈建立局部变量栈帧。替换 MSP 后再访问局部变量或执行普通 C 调用，编译器无法替你保证安全。

参考 `../examples/safer_jump_gcc.c`。更安全的设计是：

1. 首先处于特权 Thread 模式，且已经使用 MSP（若当前在 FreeRTOS PSP/Handler，先软件复位！）。
2. 在**旧栈**上完成目标校验、外设/IRQ 清理、VTOR 设置等操作。
3. 末级 `naked` 汇编函数只执行 `MSR MSP,R0; BX R1`，不要返回。
4. APP `Reset_Handler` 完成必要初始化后才显式使能 IRQ。

注意这并不能自动解决 Clock/MPU/Cache/FPU/外设状态继承，仍要根据项目检查。

## B. SRAM4 记录写入顺序

原始：

```c
JUMP_MAGIC = JUMP_MAGIC_VALUE;
JUMP_TARGET = MY_OTA_APP_ADDRESS;
JUMP_TARGET_INV = ~MY_OTA_APP_ADDRESS;
```

建议：

```c
JUMP_MAGIC = 0U;                         // 先置为无效
JUMP_TARGET = MY_OTA_APP_ADDRESS;
JUMP_TARGET_INV = ~MY_OTA_APP_ADDRESS;
__DSB();
/* 根据 Cache/MPU 配置确保目标字段已落到可见 SRAM */
JUMP_MAGIC = JUMP_MAGIC_VALUE;           // 最后发布“有效”标记
__DSB();
NVIC_SystemReset();
```

这能降低半成品请求被认作有效的概率，但三个 32 位字段依旧**不是事务性持久化记录**；如有安全升级要求，另做更稳健的记录格式。

## C. 为什么需要检查 APP 中断重新使能时机？

原代码跳转前执行 `__enable_irq()`。如果旧的 SysTick/PendSV 尚有 Pending、或新 APP 刚被进入而未初始化，风险较大。安全参考方案在分支之前保留 PRIMASK 屏蔽，APP 再在确认向量表/系统 tick 设置完成后启用 IRQ；但这样要求 APP 启动代码/`main` 配合，否则 HAL tick 和 FreeRTOS 会一直不走。

## D. 编译器和链接器的构造函数

- ST H723 GCC 启动文件的 `Reset_Handler` 会执行 `bl __libc_init_array`，因此源代码中 `constructor` 的意图在这一类工程下有明确依据。
- 你上传的代码假设 `g_pfnVectors` 是当前向量表符号，官方 ST GCC 启动文件使用该名称；Keil 不一定。
- 两个工程都需要包含 `.init_array`，若链接时把它丢了，`CheckRequestAfterReset` 不会运行。
- 如果 APP 或 Boot 使用 C++，`.init_array` 中可能还有依赖系统环境的全局构造，过早从某个构造函数直接跳转会改变其他构造函数执行顺序；复杂项目建议把请求检查移动到 Bootloader `main()` 早期。

## E. 复位标志 vs OTA 持久化状态

`SRAM4` 三个字很适合做“发生软件复位后告诉 Bootloader 下一步做什么”的**单次 IPC**，但不适合做可靠的 OTA 事务日志。

真正 OTA 应把 `DOWNLOADING`、`READY`、`INSTALLING`、`TESTING`、`CONFIRMED` 等存入**非易失性区**；重复写的 Flash 元数据还需要磨损与断电原子性设计。

## F. Cache / MPU 特别注意（STM32H7）

H7 Cortex-M7 可能开启 I-Cache、D-Cache 与 MPU。对 SRAM4 固定地址写入后，数据是否可在 SYSRESETREQ 后由新的启动代码读取，应结合缓存属性和实测确定。如果写入的是 write-back cacheable 区域，考虑在复位前按规范清理对应 D-Cache line 或将此区域设为合适的非缓存属性。**`volatile` 不等于 Cache Clean**。

## G. 关于 Flash 写入的 H7 特有风险

该源码根本没有 IAP 擦写。未来新增时，H723 这一类 Flash 的**128 KiB 扇区**、256-bit Flash word、ECC、H7 Flash HAL API 与 F407 的字节/半字/字编程模型并不等价。不能照抄 F4 的 `FLASH_TYPEPROGRAM_WORD` 示例进 H7 项目。

## H. 何时不应该使用“直接软件跳转”？

- 当前在 ISR 或 FreeRTOS PSP 任务内；
- Bootloader/APP 的 Cache、MPU、时钟配置非常复杂且无完整清理方案；
- 代码有 DMA、外设中断持续触发、调试或看门狗要求；
- 需要在各种冷启动/热启动、系统复位和异常复位后具有完全一致的行为。

这时应优先考虑**复位后由 Bootloader 判断非易失性或 SRAM 请求，再决定应用启动**，避免从复杂运行现场直接改栈切程序。
