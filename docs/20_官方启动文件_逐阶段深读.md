# 20｜对照 ST 官方 STM32H723 GCC 启动文件：从复位入口到 constructor、main

> 原始来源：https://github.com/STMicroelectronics/cmsis-device-h7/blob/master/Source/Templates/gcc/startup_stm32h723xx.s 。本章**不复制整份官方启动源**，只做流程解读并辅以自编的等价伪代码。不同 CubeMX/CubeIDE/HAL 版本可能存在差异，请以你的工程版本为准。

## 1. 从“硬件复位”到“C 函数 main”至少有三层

```text
第一层：ARM/Cortex-M 硬件复位
  → 根据设备启动配置确定映射地址
  → 读初始 MSP，读 Reset 向量，进入 Thread/特权/MSP

第二层：启动汇编 Reset_Handler（编译器/厂商工程）
  → 重新设置初始 SP（该 ST 示例存在此操作）
  → ExitRun0Mode（本 H723 GCC 模板含此供电/运行模式步骤）
  → SystemInit
  → 按链接符号把 .data 初始化值从 Flash 拷到 RAM
  → 清零 .bss
  → __libc_init_array，执行有需要的静态构造函数
  → main

第三层：你的应用 main
  → HAL_Init、时钟配置、初始化外设
  → [若 APP 使用 FreeRTOS] 创建任务并开始调度
```

**为何把硬件和软件分开？** 复位硬件“读取向量表前两个字”只负责确定初始执行入口，并不会由硬件把 `.data` 搬运好；那些是 `Reset_Handler` 和运行库的职责。

## 2. 官方符号：为什么 `g_pfnVectors` 能代表“我是谁”？

ST 官方 GCC 模板在 `.isr_vector` 段导出 `g_pfnVectors`，链接脚本把该段放在目标镜像 Flash 起始处。

- Bootloader 的 `&g_pfnVectors[0]` 应为 `0x08000000`；
- APP 的 `&g_pfnVectors[0]` 应为 `0x08020000`；
- 若其中一个工程仍显示 `0x08000000`，大概率链接脚本或向量表放置有问题。

需要强调：`g_pfnVectors` **是链接器符号指向的地址**，而向量表第 0 项存的是**栈顶数值**。它们是两个不同概念。

```c
uint32_t this_image_base = (uint32_t)&g_pfnVectors[0];
uint32_t initial_msp = g_pfnVectors[0];
uint32_t reset_entry = g_pfnVectors[1];
```

上面是教学理解；实际用户源代码使用了 `extern const uint32_t g_pfnVectors[]` 以及强制转换写法。

## 3. `.data`、`.bss` 和你 SRAM4 的 12 字节

```c
static int a = 2026;   // .data，RAM中运行，Flash保存初始值
static int b;          // .bss，启动阶段置0
const int c = 7;      // 常位于只读区域，具体取决于链接
```

因此：

- `a` 并不是“在 Flash 中直接修改”，而是启动时把初值复制到 RAM；
- `b` 不是保持上次复位的随机数据，通常会清零；
- `0x38003FF4..0x38003FFF` 的 SRAM4 记录**必须避开数据段、堆、任务栈、DMA**，否则构造函数还未读它，就可能被启动过程改写；
- “使用固定地址，启动代码就一定不会动到”并无保证；必须在实际 `.ld/.sct` 中留出。

## 4. constructor 究竟在哪里被调用？

你原代码中：

```c
__attribute__((constructor))
static void MY_OTA_JUMP_CheckRequestAfterReset(void)
{
   /* ... */
}
```

在上述 GCC 模板下，`Reset_Handler` 会执行运行库的 `__libc_init_array`，该函数遍历相关构造函数表，包括编译器放入 `.init_array` 的项目函数。于是逻辑位于**`main` 之前，但不是复位硬件自动调用**。

```text
Reset_Handler
   → __libc_init_array
        → MY_OTA_JUMP_CheckRequestAfterReset()
             → (检查 SRAM4)
             → 可能进入另一个镜像 Reset_Handler
   → main()   // 只有没有跳走时执行
```

注意 `.init_array` 必须被链接保留（通常有 `KEEP`）；开启 LTO 或变更运行库/启动文件后，应在 map 和断点中再次确认此函数存在并执行。

## 5. 目标 Reset_Handler 会做第二次初始化吗？

**会。** Bootloader 已经执行过自己的数据搬运，但 APP 的 `Reset_Handler` 会按 APP 自己的链接配置再次执行它的 `.data/.bss` 初始化。两边运行时可以独立，但同时要防止 APP 初始化把 SRAM4 请求区错误清掉（你的代码在 Boot 构造函数跳转前已清掉，这是一次性消费）。

还有一个工程性限制：**软件跳转并不等于再次硬件复位。** APP 启动文件可能假设外设、MPU、Cache、PRIMASK、时钟处于默认状态；Bootloader 没有复位就直接进入 APP 时，必须审查初始化流程能否处理当前状态。

## 6. 为什么 ST 的启动代码里会有第二次加载 SP？

硬件复位时读取初始 MSP；官方 GCC 模板进入 `Reset_Handler` 后还存在 `ldr sp, =_estack` 形式的显式栈初始化。这是启动软件主动设栈，与硬件复位机制不冲突。这也说明“APP 跳到 Reset_Handler”与“CPU 真正执行了一次硬件复位”不是同一个事情：后者由硬件设置更多状态，前者只是从指定代码入口执行。

## 7. Reset_Handler 改写 VTOR 的陷阱

有些 STM32 H7 工程的 `SystemInit` 或宏 `USER_VECT_TAB_ADDRESS` 会配置 VTOR。即使 Bootloader 刚执行：

```c
SCB->VTOR = 0x08020000;
```

如果 APP 的早期 `SystemInit` 又把 VTOR 设回 `0x08000000`，后续中断就可能跑到 Bootloader 向量表。因此不能只在 Bootloader 观察一次 VTOR；还要在**APP main** 再观察一次。

## 8. 软件复位为什么可能仍从 Boot 启动？

STM32H723 系列的启动选择受到 BOOT 配置/相关 option bytes 控制；默认设计若把用户 Flash Boot 起点指向 `0x08000000`，那么执行 `NVIC_SystemReset()` **重新启动的是 Boot 默认入口**。SRAM4 记录在之后才由 constructor 读取，不会直接改变 BOOT option bits。

> 如果用户修改了 BOOT 配置或硬件 Boot 引脚，实际首次执行的位置可能不同；所有双向跳转时序均以“默认 Boot 在 0x08000000”这一前提成立。

## 9. 应该在自己的 Keil/CubeIDE 工程核对的 10 个点

1. 当前真实芯片是否为 H723VE、512 KiB Flash？
2. Boot 配置是否选中用户 Flash 启动？
3. 两个链接脚本分别设置了哪个 `FLASH ORIGIN`？
4. `g_pfnVectors` 在 map 文件中分别等于什么？
5. 两镜像初始 MSP 的具体值、栈区域是什么？
6. `Reset_Handler` 是否调用 `ExitRun0Mode` / `SystemInit`？
7. `.data/.bss` 初始化段是否在程序跳转时可重复执行？
8. `.init_array` 是否存在、是否 `KEEP`、构造函数是否被调用？
9. APP `SystemInit` 之后，VTOR 是否仍是 APP 的地址？
10. `PRIMASK=1` 的直接跳转策略是否与 APP 启用中断的时机一致？
