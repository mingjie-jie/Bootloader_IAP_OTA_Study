# 01 | Bootloader、IAP、OTA 概念与本代码的能力边界

## 一、概念并列，不要混为一谈

| 术语 | 本质 | 负责的主要问题 | 是否一定需要联网 |
|---|---|---|---|
| Bootloader | 一段引导固件 | 决定运行哪个镜像、如何跳转、如何进入恢复模式 | 否 |
| IAP | 运行时对 MCU 的程序存储器进行重新编程的技术 | 如何接收、擦除、编程和验证新程序 | 否 |
| OTA | 通过无线网络交付更新的技术/流程 | 如何发现版本、下载、授权、部署、反馈结果 | 通常是 |

最常见的组合：**网络模块下载（OTA）→ MCU 写入 Flash（IAP）→ Bootloader 检查并启动 APP**。也可以使用 UART 进行 IAP，而完全没有 OTA；还可以先把完整镜像写到外部 Flash，再由 Bootloader 执行最终安装。

## 二、从上传源码看，已实现哪些函数？

1. `MY_OTA_JUMP_IsStackValid(address)`：判断一个 MSP 候选地址是否落在代码允许的片内 SRAM 范围。
2. `MY_OTA_JUMP_IsApplicationValid()`：从目标向量表首两个字读取 MSP 和 Reset_Handler，做初步合法性判断。
3. `MY_OTA_JUMP_JumpNow()`：清理部分中断状态，切换 VTOR、MSP，并进入目标复位入口。
4. `MY_OTA_JUMP_CheckRequestAfterReset()`：经 `constructor` 机制在 main 之前执行，消费一次性请求。
5. `MY_OTA_JUMP_Request()`：写 SRAM4 请求并调用 `NVIC_SystemReset()`。

所有上述函数的源码都保留于 `../original/`。

## 三、没有实现的功能（不要误判）

- **没有**读取 UART 数据帧 / 下载 `.bin` / HTTP 或 MQTT。
- **没有** `HAL_FLASH_Unlock`、扇区擦除或 Flash 编程函数。
- **没有** CRC32、SHA-256、签名或版本号验证。
- **没有**完整镜像长度判断 / 有效固件状态管理 / 回滚。
- **没有** Flash 双 APP 或写入暂存区的具体实现。
- **没有**用于跨断电保存的升级元数据（此处 SRAM4 仅用于**软件复位**的短期请求）。

因此该文件更准确的名字是：**SRAM4 跳转请求与软件复位后的双工程切换模块**。

## 四、学习顺序

1. 先理解**上电取 MSP 和 Reset_Handler**。
2. 再理解 **Bootloader 和 APP 的不同链接地址**。
3. 理解**从 UART IRQ 触发复位，再在 Thread 模式跳转**的原因。
4. 理解 `VTOR`、`CONTROL`、`MSP`、NVIC 清理。
5. 最后设计真实的 IAP/OTA 下载、写 Flash、校验与失败回滚。

> 原始代码注释里“Application”的名字并不是绝对角色：相同的 `.c` 文件分别放在两个工程中，`MY_OTA_APP_ADDRESS` 指代的是**本工程希望去的目标镜像**。这也是为何两边需要不同头文件。
