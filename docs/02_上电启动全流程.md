# 02 | STM32H723 从复位到 main 的完整启动流程

## 1. 第一阶段：复位时硬件做了什么？

在正常配置为从用户主 Flash 的 `0x08000000` 启动的情形下：

1. 芯片发生上电复位或软件系统复位；实际启动目标依 BOOT 配置、Option Bytes 等确定，不应把 `0x08000000` 当作**所有**启动模式的固定入口。
2. Cortex-M7 从选中的启动向量表中取出第 1 个 32 位字，作为初始 **MSP**。
3. 从第 2 个 32 位字取出 **Reset_Handler** 地址，开始执行。
4. 硬件进入 Thread 模式、特权级、使用主栈 MSP。复位入口是**启动汇编**，不是 C 的 `main()`。

例如 Bootloader 以 `0x08000000` 开始：

```text
0x08000000：初始 MSP       -> 例如 0x20020000
0x08000004：Reset_Handler  -> 例如 0x08001235（Thumb 位=1）
0x08000008：NMI_Handler
0x0800000C：HardFault_Handler
...
```

注意：上述 `0x20020000 / 0x08001235` 都是**演示数值**，真实值必须检查你自己 `.elf`、`.map` 和 `.bin`。

## 2. 第二阶段：Reset_Handler 做了什么？

针对 ST GCC 官方 `startup_stm32h723xx.s`（实际启动文件版本要核对），大致顺序：

```text
Reset_Handler:
    ldr sp, =_estack        ; 再设置栈指针
    bl ExitRun0Mode         ; H723 特定供电/运行模式初始化（视版本）
    bl SystemInit          ; 核心系统初始化
    ... copy .data         ; 把有初值的全局/静态变量从 Flash 搬到 RAM
    ... zero .bss          ; 把无显式初值的全局/静态变量清零
    bl __libc_init_array   ; 调用 .init_array 中的构造函数
    bl main                ; 进入应用 main
```

这段是**流程节选，不是完整启动文件**。官方原文：
https://github.com/STMicroelectronics/cmsis-device-h7/blob/master/Source/Templates/gcc/startup_stm32h723xx.s

### 为什么 `.data` 和 `.bss` 要初始化？

```c
uint32_t a = 123;  // .data：复位后必须变为 123
uint32_t b;        // .bss ：复位后必须变为 0
```

程序代码通常存 Flash，而普通变量在 RAM。`a` 的初始值预存 Flash，启动时复制进 RAM；`b` 所在 RAM 清零。**这会直接影响 SRAM4 保留请求：保留的 12 字节不能被链接为会被启动代码初始化的 `.data/.bss`，也不能被其他任务、栈或 DMA 覆盖。**

## 3. 第三阶段：为何原代码可以在 main 之前执行？

```c
__attribute__((constructor))
static void MY_OTA_JUMP_CheckRequestAfterReset(void)
{
    ...
}
```

对启用了 GNU `constructor` 支持、且启动流程执行 `__libc_init_array()` 的工程，编译器把函数入口挂到 `.init_array`；启动代码在进入 `main` 之前调用该函数。**这不是中断，也不是芯片自动识别函数名。**

此时已从先前触发复位的 UART ISR 返回（系统复位消除了之前的执行上下文），CPU 位于新启动的 Thread 模式，适合执行 Boot→APP 切换。但它尚处于**main 前**：不要使用依赖 UART 初始化、HAL tick、FreeRTOS 的接口。

> Keil Arm Compiler 5、部分自定义启动文件或禁用初始化数组的链接配置，不保证此机制直接成立。应检查 `.map`、`.init_array` 和实际反汇编；也可以更直观地在 Bootloader `main()` 最开始显式检查一次性请求。

## 4. 第四阶段：Bootloader 怎样跳到 APP？

APP 链接起点为 `0x08020000`：

```text
0x08020000：APP 初始 MSP
0x08020004：APP Reset_Handler
0x08020008：APP NMI_Handler
...
```

Bootloader 不能只调用 APP `main()`，因为 APP 的 `.data`、`.bss`、`SystemInit`、C/C++ 初始化、运行时和中断表还没有按要求建立。因此正确的目标是 APP **Reset_Handler**。

原代码：

```c
app_stack = *(volatile uint32_t *)MY_OTA_APP_ADDRESS;
app_reset = *(volatile uint32_t *)(MY_OTA_APP_ADDRESS + 4UL);
app_entry = (MY_OTA_JUMP_EntryFunction)app_reset;
```

后续通过 `SCB->VTOR = 0x08020000` 配置向量表基址；设置 APP 的 MSP，再跳到 APP `Reset_Handler`。

### 为什么 APP Reset_Handler 一运行还要重新初始化？

因为它是**另一个独立的固件镜像**：包含自己的系统启动初始化和 `main()`。即使 Bootloader 已经完成初始化，APP 也不应默认 Bootloader 的外设、栈和时钟配置恰好符合自己要求。

### 为什么重启后不能直接从 APP 向量表起步？

原代码调用的是 `NVIC_SystemReset()`，而**软件复位后的硬件启动位置仍由 BOOT 配置决定**，并不会因为 SRAM4 中写了目标地址就改变硬件启动地址。SRAM4 信息要由**已启动的 Bootloader 代码自己读取**；所以才需要额外的 constructor 进行软件层面的条件跳转。

## 5. 为什么 APP 切换 VTOR 特别重要？

`SCB->VTOR` 指定后续异常/中断通过哪张向量表找 ISR。即使 APP 进入了自己的 `Reset_Handler`，也要检查 `SystemInit()` 是否再次改变 VTOR。在 APP 的正式启动配置中确保最终 VTOR 为 `0x08020000`。否则业务代码看似运行正常，但触发 UART、SysTick、PendSV 后进入 Bootloader 的 ISR，常见结果是 HardFault 或卡死。

## 6. 与 FreeRTOS 的联系

- **硬件复位**：读取向量表，初始化 MSP，进入 `Reset_Handler`。
- **FreeRTOS 任务创建**：为每个任务构建初始任务栈帧，供调度器使用。
- **FreeRTOS PendSV**：保存/恢复任务上下文，通常以 PSP 管理任务栈；中断处理使用 MSP。
- **Bootloader 跳 APP**：不是恢复一个暂停的任务，而是按另一镜像的复位入口**重新开始执行初始化**。

理解 MSP、PSP、EXC_RETURN 和 PendSV 后，再看 Bootloader，会更清楚两种“切换”的本质区别。
