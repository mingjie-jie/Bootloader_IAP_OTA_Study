# 19｜案例题、故障注入与答案：判断你的理解是否真正到位

> 建议先做题再看下面答案。这些故障是**要在调试板上安全演练的场景**；不要在运行中擦除唯一可恢复的固件。

## A. 启动与寄存器场景

**A1.** Boot 在 `0x08000000`，APP 在 `0x08020000`。APP 的头文件 `MY_OTA_APP_ADDRESS=0x08000000`。APP 发出请求并复位，CPU 首先执行哪个 `Reset_Handler`？

**A2.** `SCB->VTOR=0x08020000` 后，CPU 的 PC 是否立刻变为 APP Reset_Handler？

**A3.** `__set_MSP(0x20020000)` 以后，CPU 是否自动以该地址为 PC？

**A4.** `app_entry=(void(*)(void))0x08020439;` 是否已经执行了 APP？

**A5.** APP 向量表 Reset_Handler 值为 `0x08020438`，为什么 `(value&1)==0` 有风险？

**A6.** `__disable_irq()` 后还有什么异常可发生？

**A7.** 在 UART_IRQHandler 里 `SCB->VTOR=APP_BASE; BX app_reset`，为什么不是完整的异常退出？

**A8.** `CONTROL.SPSEL=1` 且当前处于 Handler Mode，真正使用的栈是 MSP 还是 PSP？

**A9.** 改 VTOR 后 APP 接收 UART 中断失败，哪 3 个地方优先查？

**A10.** 只判断 MSP 属于 SRAM 就可以证明镜像安全完整吗？

## B. FreeRTOS 场景

**B1.** PendSV 入口，任务 PC 在哪里？为什么汇编经常看不到显式保存 PC？

**B2.** `MRS R0, PSP` 后 R0 是 PSP 的存储地址还是 PSP 寄存器当前的**数值**？

**B3.** R2 中保存指针 `0x20004000`，任务切换要把 `0x20004000` 的整片内存复制到新任务栈里吗？

**B4.** `LDR R3,=pxCurrentTCB; LDR R2,[R3]` 两次取值有什么区别？

**B5.** `BX LR` 且 LR=`0xFFFFFFFD`，是正常函数返回吗？

**B6.** SysTick 已请求 PendSV，但 BASEPRI 正在屏蔽其优先级，任务会立即切吗？

**B7.** `osDelay` 为什么可能让其他任务运行，而不需要忙等？

**B8.** 第一个 FreeRTOS 任务尚未执行过，SVC 从哪里拿初始 PC？

**B9.** Cortex-M7 启用 FPU 后，能否照抄不保存 FP 寄存器的 PendSV？

**B10.** 任务使用 PSP，执行中断用哪一个栈？

## C. IAP/OTA 场景

**C1.** 固件通过 Wi-Fi 下载成功，是否已经意味着 OTA 安装完成？

**C2.** `JUMP_MAGIC`+目标反码能防攻击者提交伪固件吗？

**C3.** 512KiB H723VE、Boot 128KiB、APP 300KiB，还能在片内保留 300KiB 完整备份吗？

**C4.** 正在擦除 APP 后掉电，为什么 SRAM4 的跳转请求不能承担恢复状态记录？

**C5.** 只用 CRC32 检查 `.bin`，是不是等于对固件签名验证？

**C6.** 双槽中把同一份链接到 0x08020000 的 `.bin` 简单写到 0x08040000 就一定能运行吗？

**C7.** 新 APP 能执行 `main()`，就能立刻标记 `CONFIRMED` 吗？

**C8.** ESP32 只缓存在易失性 RAM 下载固件，不留外部暂存，STM32 安装中掉电可能怎样？

## D. 参考答案与解释

| 题号 | 答案与推理 |
|---|---|
| A1 | 通常先 Boot 的 Reset_Handler，因为软件复位走默认启动映射；Boot constructor 后发现 target 是自身，直接继续 main。 |
| A2 | 不会。VTOR 只改异常向量查表基址。 |
| A3 | 不会。MSP 是栈指针，不是 PC。 |
| A4 | 不会。该语句只做指针赋值；真正调用是 `app_entry()`。 |
| A5 | Cortex-M 采用 Thumb，函数入口值 bit0 应置 1；否则可能引发 INVSTATE/UsageFault。 |
| A6 | NMI、特定故障仍可能发生；PRIMASK 不是全系统停机。 |
| A7 | ISR 处于 Handler Mode，普通 BX 不是 EXC_RETURN；活动异常不会自动被普通分支清除。 |
| A8 | MSP。Handler Mode 始终用 MSP。 |
| A9 | VTOR 是否被目标 SystemInit 覆盖、NVIC/外设 pending 与 enable、APP 时钟和 IRQ Handler 是否正确。 |
| A10 | 不可以，还要长度、内容、哈希与签名等。 |
| B1 | 在 PSP 上的硬件基本异常帧；硬件异常入口已自动保存。 |
| B2 | PSP 寄存器的 32 位数值（即指向任务栈的地址），不是 PSP 这个寄存器自己的内存地址。 |
| B3 | 不需要，保存指针寄存器值，原始 RAM 数据仍然存在。 |
| B4 | 第一条取得变量的地址，第二条解引用得到 TCB 指针。 |
| B5 | 是异常返回标记，CPU 根据编码从 PSP 恢复基本帧并返回 Thread。 |
| B6 | 不能马上响应 PendSV，保持 pending 直到允许。 |
| B7 | 延迟阻塞任务，调度器可选择其他就绪任务；不是 while 忙等。 |
| B8 | 任务创建时移植层构造了初始栈帧，含任务入口 PC。 |
| B9 | 不能盲目照抄；浮点上下文要按 M7 端口和 EXC_RETURN 处理。 |
| B10 | Handler Mode 用 MSP。 |
| C1 | 不一定，还要验证、持久化、安装、重启、自检确认。 |
| C2 | 不能，反码/魔数只用于偶发错误检查。 |
| C3 | 不够。片内剩余仅 384KiB，本身容纳 300KiB APP 后无法再容纳同样大小备份。 |
| C4 | 断电 SRAM 不保留，而且跳转请求不是完整 OTA 安装事务日志。 |
| C5 | 不是。CRC32 不提供可信发布者认证。 |
| C6 | 不能保证。绝对地址代码、向量表与链接符号可能不匹配。 |
| C7 | 不应，需完成真正的业务自检和确认。 |
| C8 | 可能失去安装源；需要稳定暂存与可恢复 Bootloader。 |

## E. 安全故障注入计划

| 测试序号 | 条件 | 预期行为 | 是否可以只靠现有源码实现 |
|---|---|---|---|
| 01 | 无跳转请求，正常上电 | 默认 Boot 启动 | 是，需完整双工程环境 |
| 02 | APP 请求进入 Boot | 复位后进入 Boot main | 是，需正确启动配置 |
| 03 | Boot 请求进入 APP | 复位后经构造函数分支到 APP | 是，但原 JumpNow 有风险 |
| 04 | APP 向量表前两个字为 `0xFFFFFFFF` | `IsApplicationValid=0`，不跳转 | 是 |
| 05 | TARGET 和反码不匹配 | 忽略 SRAM4 请求 | 是 |
| 06 | PRIMASK 保持 1 | APP 中断不走，需按策略启用 | 需额外日志/测试 |
| 07 | 下载中断电 | 续传或恢复 | 否，需要 IAP/OTA 扩展 |
| 08 | 擦除中断电 | Bootloader 继续安全安装 | 否，需要持久化安装状态/恢复镜像 |
| 09 | 新 APP 看门狗循环复位 | 超限回滚旧版 | 否，需要事务状态与可恢复旧版 |
| 10 | 签名无效但 CRC 正确 | 拒绝安装 | 否，需要签名验证 |

**建议先完成 01–06，且在可安全重新烧录的测试板上进行。**
