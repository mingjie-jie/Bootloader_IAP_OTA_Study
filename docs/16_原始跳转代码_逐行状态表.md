# 16｜原始 `MY_OTA_JUMP.c/.h` 的逐行执行与寄存器状态表

> 以**用户上传源码原样**为依据。对应文件：[original/MY_OTA_JUMP.c](../original/MY_OTA_JUMP.c)、[original/MY_OTA_JUMP.h](../original/MY_OTA_JUMP.h)。这是讲解，不私自把用户代码改成另一个实现。

## 1. 当前是哪一个工程版本？

上传头文件写着：

```c
#define MY_OTA_APP_ADDRESS    0x08000000UL
#define MY_OTA_APP_FLASH_END  0x08020000UL
```

说明**这个配置面向“当前 APP 位于 0x08020000、请求返回 Bootloader 0x08000000”**的方向。原注释却多处称其为 Application，容易误导；这只是命名，真实语义取决于两个工程各自的宏值。

## 2. 全部关键符号精读

| 原代码 | 数据类型或位宽 | 功能 | 必须确认 |
|---|---|---|---|
| `JUMP_MAGIC_ADDRESS = 0x38003FF4` | 地址常量 | 指向 SRAM4 保留区第 1 个字 | 链接器/DMA 不占用 |
| `JUMP_TARGET_ADDRESS = 0x38003FF8` | 地址常量 | 第 2 个字存目标程序基址 | 必须为受支持的启动地址 |
| `JUMP_TARGET_INV_ADDRESS = 0x38003FFC` | 地址常量 | 第 3 个字存目标地址逐位反码 | 仅用于意外位错检测，不是授权校验 |
| `JUMP_MAGIC_VALUE = 0x4A554D50` | `uint32_t` | ASCII `'JUMP'` | 不是加密令牌 |
| `g_pfnVectors[]` | `extern const uint32_t[]` | 当前镜像向量表链接符号 | 启动文件必须导出同名符号 |
| `MY_OTA_JUMP_EntryFunction` | `void (*)(void)` | 无参数无返回函数指针类型 | 转换只是告诉编译器怎样分支 |

## 3. `MY_OTA_JUMP_IsStackValid` 逐分支

原作者允许以下区域：

```text
DTCM   0x20000000 ... 0x20020000
AXI    0x24000000 ... 0x24050000
SRAM1/2 0x30000000 ... 0x30008000
SRAM4  0x38000000 ... 0x38003FF4 (末12字节保留)
```

`>= 起点` 可能接受向下增长栈无法继续压栈的底部位置；不检查 8 字节对齐。改进写法应要求 `sp > low && sp <= high && (sp & 7)==0`，且这些区间与芯片、链接脚本一致。

## 4. `MY_OTA_JUMP_IsApplicationValid()` 的三个原始判断

```c
uint32_t app_stack = *(volatile uint32_t *)MY_OTA_APP_ADDRESS;
uint32_t app_reset = *(volatile uint32_t *)(MY_OTA_APP_ADDRESS + 4UL);
uint32_t reset_address = app_reset & ~1UL;
```

然后依次验证：

1. `IsStackValid(app_stack)`；
2. `reset_address >= MY_OTA_APP_ADDRESS && reset_address < MY_OTA_APP_FLASH_END`；
3. `(app_reset & 1UL) != 0`。

没有做的事：未检查固件长度、CRC、哈希、签名、版本、向量表全项、启动依赖项。**返回 1 不等于 APP 完整、安全、可正常运行。**

## 5. `MY_OTA_JUMP_Request()`：从 ISR 到硬件复位

| 顺序 | 代码 | CPU/内存变化 | 后果 |
|---|---|---|---|
| ① | `IsApplicationValid()` | 从对端 Flash 取前两个向量 | 不通过直接 return |
| ② | `JUMP_MAGIC = ...` | SRAM4 存魔数 | **当前实现先写 MAGIC，有半完成记录窗口** |
| ③ | `JUMP_TARGET = ...` | SRAM4 存目标地址 | 告知目标方向 |
| ④ | `JUMP_TARGET_INV = ...` | SRAM4 存反码 | 发现部分损坏 |
| ⑤ | `__DSB(); __ISB();` | 数据/指令同步屏障 | 不等于 D-Cache 必然回写 |
| ⑥ | `NVIC_SystemReset()` | 请求 SYSRESETREQ | 当前 ISR/FreeRTOS 执行被硬件复位终止 |
| ⑦ | `while(1)` | 理论上不可达 | 防御性留在本函数 |

### 不推荐的替代写法

```c
void HAL_UART_RxCpltCallback(...) {
    MY_OTA_JUMP_JumpNow();  // 错：在 ISR 中直接跨固件 BX
}
```

在 Handler Mode 调整 MSP 与 VTOR 后直接分支，不等于异常返回，可能保留活动异常状态。原设计**先软件复位**正是为了避免这一点。

## 6. 复位后 constructor 逐步分析

原函数名：`MY_OTA_JUMP_CheckRequestAfterReset`。符号使用 `__attribute__((constructor))`，前提是对应 C 运行时确实执行 `.init_array`。

| 顺序 | 动作 | 关键说明 |
|---|---|---|
| A | `current_address = (uint32_t)g_pfnVectors` | 当前工程向量表地址，与跳转目标不同 |
| B | 比较 `MAGIC` 与 `INV == ~TARGET` | 不通过 → 当前程序继续启动到 `main` |
| C | 读 `requested_target = TARGET` | 保存到局部变量以便清空保留 RAM |
| D | 清空 MAGIC / TARGET / INV | 一次性消费请求；下一次复位不重复切换 |
| E | `requested_target == current_address` | **已经到达本工程**，继续进入本工程 main |
| F | `requested_target == MY_OTA_APP_ADDRESS` | 若指向另一镜像，调用 JumpNow |
| G | 其他情况 | 无额外操作，继续当前 main |

**重点：**软件复位通常从默认启动配置规定的位置进入，而不是从 SRAM4 目标地址自动启动。`constructor` 才是软件读取并处理跳转请求的环节。

## 7. `MY_OTA_JUMP_JumpNow()`：状态表

| 次序 | 语句 | 所改状态 | 额外条件/风险 |
|---|---|---|---|
| 1 | `IsApplicationValid()` | 仅 Flash 读取 | 错误参数/存储访问可能出错 |
| 2 | `app_stack = *(base+0)` | 读初始 MSP 数值 | 尚未更改 MSP |
| 3 | `app_reset = *(base+4)` | 读 Reset_Handler 入口 | bit0 应为 1 |
| 4 | `app_entry = (function pointer)app_reset` | 定义运行时分支目标 | **没有执行跳转** |
| 5 | `__disable_irq()` | PRIMASK=1 | NMI/某些 Fault 仍可能发生 |
| 6 | `SysTick->CTRL/LOAD/VAL=0` | 关闭节拍并清计数 | 不会自动清 PendSV pending |
| 7 | `NVIC->ICER[i] / ICPR[i]` | 禁用/清挂起外部 IRQ | 不停止外设；依赖 IRQ bank 范围正确 |
| 8 | `SCB->VTOR = target` | 新的异常向量查找基址 | 目标向量表必须有效、对齐 |
| 9 | `__set_CONTROL(0)` | Thread 特权/MSP 等 | 当前 Thread/特权前提；不能用作 ISR 退出 |
| 10 | `__DSB/__ISB` | 同步控制状态 | 不会“自动初始化 APP” |
| 11 | `__set_MSP(app_stack)` | 换到目标主栈 | **最危险的编译器栈帧边界** |
| 12 | `__DSB/__ISB` | 屏障 | 仍无法保证后续 C 代码不访问旧帧 |
| 13 | `__enable_irq()` | PRIMASK=0 | 新 APP 初始化前发生 IRQ 的窗口 |
| 14 | `app_entry()` | 间接调用 Reset_Handler | 底层常以 BLX 形式实现，非严格无返回分支 |
| 15 | `while(1)` | 非预期返回时进入 | 如果 Reset_Handler 返回，该代码可能已处于不安全栈状态 |

## 8. 为什么“设置 MSP 后不声明局部变量”不是充分保证？

原注释写了“设置 MSP 后不要再声明局部变量，也不要再调用普通函数”，但下面仍出现 `__enable_irq()` 和 `app_entry()`。即使 C 源码不显式声明新变量，编译器**仍可能**通过旧 MSP 栈帧装载 `app_entry`，或为函数调用生成额外出入栈。要用可审查的末级汇编消除这个不确定性。

## 9. 手动演算一次 APP → Bootloader

前提：默认启动 `0x08000000`，运行中的 APP 位于 `0x08020000`，该 APP 编译时设置目标为 `0x08000000`。

```text
APP 0x08020000 正在运行，目标 0x08000000
  ↓ APP Request() 写 MAGIC/TARGET/INV
NVIC_SystemReset()
  ↓ 默认 Flash 引导：Boot 0x08000000 启动
  ↓ Boot 的 constructor 读取 requested_target=0x08000000
  ↓ requested_target == Boot 自己的 g_pfnVectors
  ↓ 清标志后直接 return
Boot main() 运行
```

**注意：这一路径可能不调用 `MY_OTA_JUMP_JumpNow()`。** 因为软件复位本来就从 Boot 默认地址启动，构造函数看到“已经在目标”就直接进入 main。对理解你代码的方向分支特别重要。

## 10. 手动演算 Bootloader → APP

Bootloader 运行在 `0x08000000`，目标是 `0x08020000`。请求复位后**首先再次进入 Bootloader**（默认启动配置不变）：

```text
Boot Request(target=0x08020000)
  ↓ SYSRESETREQ
Boot Reset_Handler, constructor
  ↓ target != Boot 自身 0x08000000
  ↓ target == Boot 配置的另一端 0x08020000
  ↓ IsApplicationValid 通过
  ↓ JumpNow: VTOR/MSP/branch
APP Reset_Handler, constructor
  ↓ SRAM4 请求已被 Boot 清空
APP main()
```

这说明“SRAM4 目标地址”不是修改硬件启动映射，而是在默认引导过程中由软件解释。

## 11. 最容易漏掉的条件

- 复位方式必须确保所用 SRAM4 数据在预期路径仍可读；**断电不保留**。
- `g_pfnVectors` 必须与链接入口一致；若不同的工具链使用不同启动符号，须适配。
- 两个工程**不能共享完全一样的 `MY_OTA_APP_ADDRESS`**；而且 `FLASH_END` 是“本端目标合法区间末地址”，不是整片末地址。
- `0x38003FF4` 这 12 字节需要在两个工程中都从 `.bss/.data/堆栈` 使用范围排除。
- 遇到 D-Cache 缓存属性时要保证 SRAM4 写入可见性；`volatile` 与 `DSB` 不是缓存清理的同义词。
