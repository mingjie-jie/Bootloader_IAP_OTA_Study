# 18｜Keil / CubeIDE / GDB 里一步步观察 MSP、PSP、VTOR、PC 和 EXC_RETURN

> 这是调试操作指导，需你本人的 STM32H723VE 板卡、烧录器与相应工程。**仓库不含你的 `.ioc`/完整 HAL 配置，不声称已实机验证。**

## 1. 测试前准备

- Bootloader 链接基址 `0x08000000`，APP 链接基址 `0x08020000`；两个工程分别校验 `.map` 文件。
- 为方便定位，先让 Boot 与 APP 输出**不同**串口日志、LED 闪烁模式。
- 两个镜像都要有自己的启动文件/向量表；不同地址烧录时防止覆盖另一个 Sector。
- 调试器连接后打开：Registers、Memory、Disassembly、Call Stack、Watch。
- `SCB->VTOR`、`__get_MSP()`、`__get_PSP()`、`__get_CONTROL()`、`__get_IPSR()`、`__get_PRIMASK()`、`__get_BASEPRI()`、`SCB->ICSR`、`SCB->CFSR`（具体 IDE 可能显示方式不同）。

## 2. 复位后的第一轮断点

1. 断在**默认启动镜像** `Reset_Handler` 的第一条指令。
2. 读取 `MSP`；对照向量表起始 4 字节，例如 `*(uint32_t*)0x08000000`。
3. 读取 PC；对照向量表第 2 个字的入口值（注意 Thumb bit0）。
4. 断在 `SystemInit`，确认时钟/VTOR/MPU 等初始化是否修改状态。
5. 断在 `__libc_init_array` 与 `MY_OTA_JUMP_CheckRequestAfterReset`，确认构造函数是否执行。
6. 断在 `main`，检查 `.data/.bss` 正常初始化。

**有意义的观察**：软件复位恢复的是**默认启动镜像的** MSP/Reset_Handler，而非直接读取 SRAM4 里想去的目标；SRAM4 是后续 C 代码读取的请求协议。

## 3. 单步追踪 Boot → APP

```text
断点 ① Boot Request()
  SRAM4: 0x38003FF4/3FF8/3FFC 三个字
  观察 TARGET 是否等于 0x08020000
断点 ② 系统复位后 Boot constructor
  观察 `g_pfnVectors` 是不是 0x08000000
  观察 requested_target 是否等于 0x08020000
断点 ③ Boot JumpNow() 入口
  读 APP `0x08020000` 与 `0x08020004`
断点 ④ VTOR 写入后
  VTOR = 0x08020000
断点 ⑤ 末级 BX 前（需要安全汇编实现）
  R0=APP MSP, R1=Reset_Handler|1
断点 ⑥ APP Reset_Handler
  MSP = APP 初始栈顶；PC = APP Reset_Handler
断点 ⑦ APP main
  检查中断与 HAL tick 已按策略恢复
```

如果直接单步从 `__set_MSP()` 进入原代码 `app_entry()`，观察是否出现编译器自动访问旧栈：切换 `-O0` 与 `-O2` 做对比，但**不要把一次能跑当成正确实现**。

## 4. 再追 APP → Boot：这个方向与上一条不同！

原头文件 `MY_OTA_APP_ADDRESS=0x08000000` 是 APP → Boot 方向：

```text
APP Request(target 0x08000000)
   → 复位
默认启动已经是 0x08000000 Boot
   → constructor 发现 requested_target == Boot g_pfnVectors
   → 清请求，继续 Boot main
```

如果这一方向没有触发 `JumpNow()`，不一定是错误；在正确默认启动配置下，反而是代码预期行为。

## 5. FreeRTOS 任务切换观察顺序

1. 观察某一任务运行时 `IPSR=0`，`CONTROL.SPSEL=1`、当前任务 PSP。
2. 触发 tick 或 `taskYIELD`；观察 `SCB->ICSR` PendSV pending 位。
3. 断在 `xPortPendSVHandler` 入口：`IPSR=14`（PendSV 系统异常号），Handler 模式使用 MSP，R14 可能为 `0xFFFFFFFD` 或 FP 扩展值。
4. 读 PSP 所指的基本异常帧：R0/R1/R2/R3/R12/旧 LR/PC/xPSR。
5. 单步 `MRS R0, PSP`、`STMDB R0!,...`，跟踪 R0 向低地址递减。
6. 看 `pxCurrentTCB->pxTopOfStack` 写成新的栈顶。
7. 单步 `vTaskSwitchContext` 后，观察 `pxCurrentTCB` 指向新 TCB。
8. 恢复新任务 R4-R11/EXC_RETURN，`MSR PSP`，`BX LR`。
9. **硬件异常返回**从新 PSP 弹 PC，程序继续运行新任务。

### 建议记录表（每次任务切换填一次）

| 观察点 | IPSR | CONTROL.SPSEL | MSP | PSP | LR | 备注 |
|---|---:|---:|---|---|---|---|
| Task A 执行 | 0 | 1 | ... | ... | 业务返回值 | 正常 Thread |
| PendSV 入口 | 14 | 1（Thread 配置） | ... | ... | EXC_RETURN | Handler 实际使用 MSP |
| 软件保存后 | 14 | 同上 | ... | TCB A 保存值 | EXC_RETURN | TCB 改写 |
| 异常返回后 Task B | 0 | 1 | ... | ... | 业务 LR | 新任务继续 |

## 6. HardFault / UsageFault 如何定位

- 首先记录 `SCB->CFSR`、`SCB->HFSR`、`SCB->MMFAR`、`SCB->BFAR`（仅相应有效位为真时使用故障地址）。
- 查看 `LR` 是否为 EXC_RETURN，判断故障发生前来自 PSP/MSP。
- 从故障时栈帧取堆栈中的 PC，结合反汇编定位是哪一条指令。
- 若 fault 出现在跳转后，重点查入口 bit0、目标存储是否正确、MSP 有效性、VTOR、启动代码与 MPU 指令访问权限。
- 若是 APP `HAL_Delay` 不走，查 SysTick 使能、PRIMASK、BASEPRI 与 tick 初始化先后顺序。

## 7. 反汇编验证推荐语句

```text
在 IDE 中分别对原始 JumpNow 和安全分支版本：
- 观察 __set_MSP() 之后是否出现 LDR [SP,...]、PUSH、POP、BLX 等
- 观察最后是否能保证 `MSR MSP,R0 ; BX R1` 相邻执行
- 检查是否在启用 IRQ 前已初始化目标向量与必要状态
- 比较 -O0 与 -O2 对指令序列的影响
```

## 8. 如遇“复位后根本不进 constructor”

查看工程中的启动文件是否导出 `g_pfnVectors`，是否执行 `.init_array`；ST 官方 GCC 版本启动示例包含 `bl __libc_init_array`。Keil 不同编译器库可能使用不同启动/构造函数机制，应按自身工程核对，不能直接认为 `__attribute__((constructor))` 在所有工具链都生效。
